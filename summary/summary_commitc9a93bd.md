# สรุป commit `c9a93bd` — Add balance batches and weight tuning with an LLM advisor

- **Branch:** `ai-sim` (ต่อจาก `0c93154`)
- **ขั้นในแผน AI:** ขั้นที่ 5 (batch CLI) + ขั้นที่ 6 (tuner, รายงาน, LLM ที่ปรึกษาแบบทำมือ)

## สรุปสั้น

1. **`npm run batch`** (โหมด A): เล่น 200 seed ขนานทุก core แล้วเขียนรายงาน balance ภาษาไทย
2. **`npm run tune`**: hill-climbing บน seed หลัก ตัดสินด้วยนัยสำคัญทางสถิติ, ตรวจ holdout เป็นระยะ และเขียนรายงานทุกรอบ ("จูนอะไร / เรียนรู้อะไร / รอบหน้าจะทำอะไร")
3. **LLM เป็นที่ปรึกษา ไม่ใช่ผู้ตัดสิน**: export คำขอ → วางในแชท → import คำตอบ JSON → ข้อเสนอต้องเล่น seed เดิมเหมือน candidate ทั่วไป และระบบตรวจว่าทายถูกหรือผิดทีละ metric
4. ผลทุกชุดถูก cache ตาม **rules hash** ถ้าโค้ดเกมหรือบอทเปลี่ยน ผลเก่าจะถูกแยกออกอัตโนมัติ

## วิธีใช้

```bash
npm run batch -- --weights=w0 --seeds=200          # รายงาน balance → sim-runs/batch/<เวลา>-w0.md
npm run tune -- --rounds=20                        # จูน 20 รอบ → sim-runs/tune/reports/round-NNN.md
npm run tune -- --export-llm                       # สร้างคำขอ → sim-runs/tune/llm/request-rNNN.md
npm run tune -- --rounds=5 --import=answer.json    # เล่นข้อเสนอของ LLM แล้วจูนต่อ
npm run tune -- --rounds=5 --try=my.json           # ลองค่าน้ำหนักที่ตั้งเอง (source: manual)
npm run tune -- --reset --start=smart              # เริ่มการจูนใหม่ (ของเดิมย้ายไป sim-runs/tune-<เวลา>)
```

ตัวเลือกอื่น: `--candidates=4`, `--seeds=200`, `--difficulty=normal`, `--threads=N`, `--holdout-every=10`, `--llm-stuck=12`, `--llm-every=25`

## หลักการที่ใช้

### ตัดสินว่า "ดีขึ้นจริง" อย่างไร

- ทุกชุดเล่น **seed หลักชุดเดียวกัน** (1–200) แล้วเทียบคะแนนกับ best **รายต่อ seed**
- รับชุดใหม่เมื่อ ค่าเฉลี่ยของผลต่าง > 0 **และ** z = ผลต่าง / standard error ≥ 2
- รอบหนึ่งรับได้แค่ชุดเดียว (ชุดที่ดีขึ้นมากที่สุด) ชุดอื่นที่ผ่านเกณฑ์ด้วยจะถูก**รวม**กับ best ใหม่แล้วลองในรอบถัดไป

### Hill-climbing

- แต่ละ candidate เปลี่ยน 1–3 ค่า (โอกาส 60% / 30% / 10%) ขนาดก้าว = ช่วงของค่านั้น × `stepScale` × 3–15%
- **จำทิศทาง**: ทุกค่าเก็บสถิติแยก "เพิ่ม" / "ลด": ชนะจริง, ดีขึ้นแต่ยังไม่ผ่านเกณฑ์ และจำนวนครั้งที่ลอง ทิศทางที่เคยได้ผลจะถูกเลือกบ่อยขึ้น
- **ทางตัน**: ลองแล้ว ≥ 3 ครั้ง ไม่เคยชนะ และส่วนใหญ่ไม่ได้ดีขึ้นเลย จะถูกเลือกน้อยลง (แต่ยังมีโอกาส)
- **`stepScale`**: ×1.25 เมื่อชนะ (สูงสุด 3), ×0.85 เมื่อไม่ชนะ (ต่ำสุด 0.3) และกระโดดเป็น 2 ครั้งเดียวตอนไม่ดีขึ้นครบ 8 รอบ เพื่อหลุดจาก local optimum
- ไม่ลองชุดที่เคยลองแล้วซ้ำ

### Holdout

ทุก 10 รอบ (`--holdout-every`) จะเล่น best บน seed ชุดที่สอง (1,000,001–1,000,200) ที่ tuner ไม่เคยใช้ แล้วเทียบ**กับจุดเริ่มของการจูน** ทั้งบน seed หลักและบน holdout ถ้าดีขึ้นบน seed หลักแต่ไม่ดีขึ้นบน holdout รายงานจะเตือนว่าอาจ overfit

### Rules hash

hash ของ `src/game/*`, `src/data/*` และ `src/ai/{bot,runner,recorder,weights}.ts` (ตัด CRLF ออกก่อน hash) ผลทุกชุดเก็บที่ `sim-runs/evals/<hash>/...` ถ้า hash เปลี่ยน ทุกอย่างจะถูกเล่นใหม่ และ tuner จะบันทึกว่า "โค้ดเกมหรือบอทเปลี่ยน" พร้อมสร้างคำขอให้ LLM ดูว่าค่าไหนควรขยับก่อน

## LLM ที่ปรึกษา

**คำขอ (`request-rNNN.md` / `.json`)** มีข้อมูลสรุปเท่านั้น ไม่มี GameRecord ดิบ:
- เหตุผลที่เรียก, จำนวนรอบที่ไม่ดีขึ้น, สูตรคะแนน, เกณฑ์การรับ
- best ปัจจุบันพร้อมค่าน้ำหนัก, **bounds** และ **คำอธิบายของทุกค่า**, สรุปพฤติกรรมบอท (รวมสิ่งที่บอทยังไม่ใช้)
- **history 40 รายการล่าสุด รวมชุดที่แพ้** พร้อมผลตรวจสมมติฐานเดิม และสถิติว่า LLM เคยช่วยได้แค่ไหน
- ตายที่ไหนและด้วยอะไร, lives ที่เสียรายด่าน, ทองตอนเริ่มเวฟ, tower 15 อันดับแรก, special ที่ทำได้หรือไม่เคยทำ
- รายชื่อ metric ที่ใช้ทายได้, `missingWeights` ที่เคยเสนอไปแล้ว และรูปแบบคำตอบ

**การตรวจคำตอบ (`parseAdvice`)**:
- รับไม่เกิน 5 ข้อเสนอ
- ตัดชื่อค่าที่ไม่มีอยู่จริงและค่าที่ไม่ใช่ตัวเลข, clamp ค่าที่เกินขอบเขต
- ข้ามข้อเสนอที่ไม่ได้เปลี่ยนอะไร หรือซ้ำกับชุดที่เคยลอง
- `expect` ต้องใช้ metric ที่มีอยู่จริง, `levels` อยู่ใน 1–50, metric ระดับ tower ต้องระบุ tower id ที่มีอยู่จริง
- ทุกปัญหาที่เจอถูกรายงาน ไม่ทำให้โปรแกรมล้ม

**หลังรัน**: แต่ละ `expect` ได้ผลเป็น ✅ ทายถูก / ❌ ทายผิด / ➖ ไม่มีผลชัดเจน จากการเทียบรายคู่ของ metric นั้น ส่วน `missingWeights` ถูกบันทึกใน `sim-runs/tune/missing-weights.md` ให้คนตัดสินใจ **ไม่มีการแก้โค้ดบอทอัตโนมัติ**

## ผลที่ได้จากการทดลองรัน

**Balance (`w0`, 200 seed):**
- ด่านเฉลี่ย 14.9, ไม่เคยชนะ
- **กำแพงหลักคือบอส Summon ด่าน 14 (37% ของเกมจบที่นี่)** เสีย lives เฉลี่ย 23.9 ในด่านนี้ ทั้งที่มีทองค้างเฉลี่ย 84
- Sterling Silver ทำ damage 24% ของทั้งหมด
- สูตร special 6 จาก 13 สูตรไม่เคยถูกทำเลย (Yellow Sapphire, Blood Stone, Uranium 238, Gold, Black Opal, Paraiba Tourmaline)

**ทดสอบเส้นทาง LLM** (คำตอบตัวอย่างที่ผมเขียนเองจากข้อมูลในคำขอ):

| ข้อเสนอ | ผล | สมมติฐาน |
|---|---|---|
| `qualityReserve` 30→0, `upgradeReserve` 20→0 | −0.48 (z −3.3) ไม่รับ | ✅ lives ที่เสียกับบอสด่าน 14 ลดลงจริง / ❌ แต่ไปได้ไม่ไกลขึ้น |
| `mazeGain` 0→1, `airValue` 1→2 | +0.35 (z 2.1) ผ่านเกณฑ์ แต่แพ้ w3 | ✅ เสีย lives ในเวฟพื้นน้อยลง / ❌ เวฟอากาศด่าน 16–24 กลับเสียมากขึ้น |
| `combine2Bonus` 1000→0 | **+0.42 (z 3.2) รับ** | ✅ คะแนนดีขึ้น |

holdout ยืนยันว่า `w3` ดีขึ้นจริง: **+0.42 บน seed หลัก / +0.53 บน holdout** ไม่ได้ overfit

## ข้อควรรู้

- **lives ที่เสียแยกตามชนิดเวฟต้องอ่านอย่างระวัง**: เกมที่แพ้เสียครบ 50 เสมอ ถ้าเวฟพื้นเสียน้อยลง ก็จะไปเสียที่อื่นแทน (เช่น maze ทำให้รอดเวฟพื้น แต่ไปตายที่เวฟอากาศ) ตัวเลขนี้จึงบอกว่า "ตายที่ไหน" มากกว่า "อ่อนตรงไหน"
- **`weights.ts` อยู่ใน rules hash**: แก้ค่าเริ่มต้นหรือ spec เมื่อไร ผลเก่าทั้งหมดจะถูกเล่นใหม่
- **IDE แจ้ง error ใน `scripts/`** เพราะโปรเจกต์ไม่มี `@types/node` (เป็นแบบนี้กับสคริปต์เดิมด้วย) `tsc` ตรวจเฉพาะ `src/` และ esbuild bundle ได้ปกติ
- `clampWeight` ปัดค่าตามช่วง: ช่วงตั้งแต่ 100 ขึ้นไปปัดเป็นจำนวนเต็ม นอกนั้นทศนิยม 2 ตำแหน่ง
